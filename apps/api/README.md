# Habit Tracker API

REST API для трекера привычек: привычки с расписанием по дням недели, отметки выполнения и статистика серий (стриков).

Учебный бэкенд на Node.js + TypeScript. Удобен как готовый сервер для практики фронтенд-разработки.

## Стек

- **Node.js 24**, **TypeScript**
- **Fastify 5** — HTTP-сервер
- **TypeBox** — схемы валидации запросов и ответов, из них же выводятся типы
- **PostgreSQL 18** + **Drizzle ORM** — база данных и миграции
- **Swagger UI** — интерактивная документация API
- **Docker Compose** — запуск сервера и базы одной командой

## Быстрый старт

Нужен только [Docker Desktop](https://www.docker.com/products/docker-desktop/). Node.js, pnpm и PostgreSQL ставить не нужно.

```bash
git clone <адрес репозитория>
cd back-habbit-tracker
docker compose up -d --build
```

Docker соберёт образ сервера, поднимет базу, применит миграции и запустит API. Первый запуск занимает пару минут, следующие — секунды.

| Что | Адрес |
|---|---|
| API | http://localhost:3000 |
| Документация (Swagger UI) | http://localhost:3000/docs |
| OpenAPI-описание в JSON | http://localhost:3000/docs/json |
| Проверка работы сервера | http://localhost:3000/health |

### Управление

| Команда | Что делает |
|---|---|
| `docker compose up -d --build` | Собрать и запустить всё |
| `docker compose stop` | Остановить, данные сохраняются |
| `docker compose start` | Запустить снова |
| `docker compose ps -a` | Статус сервисов |
| `docker compose logs -f app` | Логи сервера |
| `docker compose down` | Удалить контейнеры, данные сохраняются |
| `docker compose down -v` | Удалить контейнеры **и все данные базы** |

### CORS

По умолчанию API принимает запросы из браузера только со страниц на `http://localhost:5173` (адрес Vite dev-сервера). Если фронтенд работает на другом адресе, поменяй `CORS_ORIGIN` у сервиса `app` в `docker-compose.yml` и перезапусти: `docker compose up -d app`. Несколько адресов указываются через запятую: `http://localhost:5173,http://localhost:3001`.

## Предметная область

### Привычка (habit)

```json
{
  "id": "0b8c5f3e-6c2a-4c8e-9a51-2f1d3e4b5a6c",
  "name": "Бег",
  "activeDays": [1, 3, 5],
  "weekGoal": 2
}
```

- `activeDays` — дни недели, когда привычку нужно выполнять. Нумерация по ISO 8601: **1 — понедельник, 7 — воскресенье**. Не пустой массив без повторов, сервер хранит его отсортированным.
- `weekGoal` — сколько раз в неделю нужно выполнить привычку, чтобы неделя считалась успешной. Не больше количества активных дней. В примере выше привычка активна в понедельник, среду и пятницу, и неделя успешна, если выполнены любые два из этих дней.
- Неделя — по ISO: с понедельника по воскресенье.

### Отметка (checkin)

```json
{ "habitId": "0b8c5f3e-6c2a-4c8e-9a51-2f1d3e4b5a6c", "date": "2026-10-05" }
```

Отметка означает «привычка выполнена в этот день». Правила:

- Отметку можно поставить **только в активный день** привычки (иначе `422`).
- **Одна отметка** на привычку в день (повтор — `409`).
- Дата не позже завтрашнего дня по UTC (иначе `400`).
- При удалении привычки удаляются все её отметки.

### Даты и часовые пояса

Все даты передаются как **календарные даты** в формате `YYYY-MM-DD`, без времени. Дату выбирает **клиент** по календарю пользователя: сервер не знает часовой пояс пользователя и не пересчитывает даты. Поэтому статистика тоже принимает «сегодня» от клиента (параметр `today`).

## Эндпоинты

Полное описание с форматами запросов и ответов — в Swagger: http://localhost:3000/docs.

### Привычки

| Метод и путь | Описание | Успех |
|---|---|---|
| `GET /habits` | Список привычек (по дате создания) | `200` |
| `GET /habits/:id` | Одна привычка | `200` |
| `POST /habits` | Создать: `{ name, activeDays, weekGoal }` | `201` |
| `PATCH /habits/:id` | Изменить любые из полей `name`, `activeDays`, `weekGoal` | `200` |
| `DELETE /habits/:id` | Удалить привычку и её отметки | `204` |

### Отметки

| Метод и путь | Описание | Успех |
|---|---|---|
| `POST /habits/:habitId/checkins` | Отметить выполнение: `{ "date": "2026-10-05" }` | `201` |
| `DELETE /habits/:habitId/checkins/:date` | Снять отметку | `204` |
| `GET /checkins?from=&to=` | Отметки всех привычек за период | `200` |
| `GET /checkins/statistics?today=` | Стрики по всем привычкам | `200` |

`GET /checkins`:
- `from` — обязательный, начало периода включительно;
- `to` — необязательный, конец периода включительно. Если не указан — все отметки начиная с `from`;
- результат отсортирован по дате.

Пример: отметки всех привычек за неделю для экрана с недельным календарём:

```
GET /checkins?from=2026-10-05&to=2026-10-11
```

`GET /checkins/statistics?today=2026-10-09` возвращает для каждой привычки:

```json
[
  { "habitId": "…", "dayStreak": 4, "weekStreak": 2 }
]
```

- `dayStreak` — сколько активных дней подряд привычка выполнена (неактивные дни серию не прерывают);
- `weekStreak` — сколько недель подряд достигнута недельная цель.

Сегодняшний день и текущая неделя серию не обрывают, пока их ещё можно выполнить: неотмеченное «сегодня» не сбрасывает `dayStreak`, а текущая неделя не сбрасывает `weekStreak`, пока цель ещё достижима. Стрики считаются по текущему расписанию привычки (`activeDays`).

## Ошибки

Все ошибки возвращаются в одном формате:

```json
{
  "code": "CHECKIN_INACTIVE_DAY",
  "message": "Can not create checkin for habit's inactive day"
}
```

- `code` — машиночитаемый код. **Фронтенд опирается на него**: по коду выбирается понятный пользователю текст. Коды — часть API и не меняются.
- `message` — техническое описание на английском, для отладки. Пользователю его не показывать: текст может меняться.
- `details` — есть только у ошибок валидации схемы запроса (`VALIDATION_ERROR`), см. ниже.

### Коды ошибок

**Общие**

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Запрос не прошёл валидацию схемы. Подробности по полям — в `details` |
| 400 | `BAD_REQUEST` | Некорректный запрос: битый JSON, неверный `Content-Type` и т.п. |
| 404 | `ROUTE_NOT_FOUND` | Такого эндпоинта нет |
| 500 | `INTERNAL_ERROR` | Ошибка на сервере |

**Привычки**

| HTTP | `code` | Когда |
|---|---|---|
| 404 | `HABIT_NOT_FOUND` | Привычки с таким `id` нет. Также при создании отметки для несуществующей привычки |
| 400 | `HABIT_GOAL_EXCEEDS_DAYS` | `weekGoal` больше количества активных дней. При `PATCH` проверяется итоговая привычка: например, если уменьшить `activeDays`, а старый `weekGoal` перестал помещаться |
| 400 | `HABIT_NAME_EMPTY` | Имя состоит только из пробелов |
| 400 | `HABIT_DAYS_EMPTY` | `activeDays` пустой. На практике приходит как `VALIDATION_ERROR` — схема проверяет это раньше |
| 400 | `HABIT_DAYS_NOT_UNIQUE` | В `activeDays` повторы. На практике приходит как `VALIDATION_ERROR` — схема проверяет это раньше |

**Отметки**

| HTTP | `code` | Когда |
|---|---|---|
| 404 | `CHECKIN_NOT_FOUND` | Снимаемой отметки нет |
| 409 | `CHECKIN_ALREADY_EXISTS` | Отметка на эту дату уже есть |
| 422 | `CHECKIN_INACTIVE_DAY` | День недели даты не входит в `activeDays` привычки |
| 400 | `CHECKIN_FUTURE_DATE` | Дата позже завтрашнего дня по UTC |
| 400 | `CHECKIN_INVALID_DATE_RANGE` | В `GET /checkins` параметр `to` раньше `from` |

Неизвестный фронтенду код стоит показывать общим сообщением об ошибке: новые коды могут появляться.

### Ошибки валидации (`details`)

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "details": [
    { "path": "body/activeDays/0", "message": "must be <= 7" }
  ]
}
```

`path` — где ошибка: `body`, `params` или `querystring`, затем путь к полю. `message` — текст валидатора на английском.

| Эндпоинт | Возможные `path` |
|---|---|
| `POST /habits` | `body/name`, `body/activeDays`, `body/activeDays/<индекс>`, `body/weekGoal`, `body` |
| `PATCH /habits/:id` | то же, что у `POST`, и `params/id` |
| `GET /habits/:id`, `DELETE /habits/:id` | `params/id` |
| `POST /habits/:habitId/checkins` | `params/habitId`, `body/date`, `body` |
| `DELETE /habits/:habitId/checkins/:date` | `params/habitId`, `params/date` |
| `GET /checkins` | `querystring/from`, `querystring/to`, `querystring` |
| `GET /checkins/statistics` | `querystring/today`, `querystring` |

- `body/activeDays` — ошибка массива целиком (пустой или с повторами), `body/activeDays/2` — ошибка конкретного элемента (не целое или вне 1–7).
- **Отсутствующее обязательное поле** даёт `path` объекта, а не поля: `POST /habits` без `name` вернёт `{ "path": "body", "message": "must have required property 'name'" }`. Имя поля есть только в тексте сообщения. Тот же `path: "body"` — у `PATCH` с пустым телом.
- **В `details` сейчас всегда одна ошибка** — валидатор останавливается на первой. Если неверны два поля, придёт только одно.
- Лишние поля в теле запроса ошибкой не считаются — сервер их молча отбрасывает.

## Типы для фронтенда

TypeScript-типы запросов и ответов можно сгенерировать из OpenAPI-описания работающего сервера, например пакетом [openapi-typescript](https://openapi-ts.dev/):

```bash
npx openapi-typescript http://localhost:3000/docs/json -o src/api/schema.d.ts
```

## Локальная разработка

Для работы над самим сервером без сборки Docker-образа.

**Нужно:** Node.js 24, pnpm (версия зафиксирована в `package.json`, включается командой `corepack enable`), Docker Desktop для базы.

```bash
pnpm install
cp .env.example .env    # и при необходимости поправить значения
pnpm db:up              # запустить только PostgreSQL в Docker
pnpm db:migrate         # применить миграции
pnpm dev                # сервер с перезапуском при изменениях
```

Сервер в Docker (`app`) и `pnpm dev` используют один порт 3000 — одновременно работает только один из них.

### Переменные окружения

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATABASE_URL` | — (обязательная) | Строка подключения: `postgres://user:password@host:5432/db` |
| `NODE_ENV` | `development` | `development` — читаемые логи, `production` — логи в JSON, `test` — без логов |
| `HOST` | `0.0.0.0` | На каком интерфейсе слушать |
| `PORT` | `3000` | Порт |
| `CORS_ORIGIN` | `http://localhost:5173` | Разрешённые адреса фронтенда через запятую |

При невалидном значении сервер не стартует и сообщает, какая переменная неверна.

### Скрипты

| Скрипт | Что делает |
|---|---|
| `pnpm dev` | Запуск в режиме разработки |
| `pnpm build` / `pnpm start` | Сборка в `dist` и запуск собранного сервера |
| `pnpm typecheck` | Проверка типов |
| `pnpm lint` / `pnpm lint:fix` | Линтеры |
| `pnpm test` | Тесты (Vitest) |
| `pnpm db:up` / `pnpm db:down` | Запустить / остановить базу |
| `pnpm db:psql` | Консоль PostgreSQL |
| `pnpm db:generate` | Сгенерировать миграцию из изменений в `*.table.ts` |
| `pnpm db:migrate` | Применить миграции |
| `pnpm db:studio` | Drizzle Studio — просмотр данных в браузере |
| `pnpm db:reset` | **Удалить базу со всеми данными** |

### Миграции

Структура базы меняется только через миграции:

1. изменить таблицу в `src/modules/**/*.table.ts`;
2. `pnpm db:generate --name <описание>` — создаст SQL-файл в `drizzle/`;
3. прочитать сгенерированный SQL;
4. `pnpm db:migrate` — применить.

Папка `drizzle/` коммитится целиком. Уже применённые миграции не редактируются — нужна новая. В Docker миграции применяет сервис `migrate` перед стартом сервера.

## Структура проекта

```
src/
  server.ts              точка входа: запуск и корректная остановка сервера
  app.ts                 сборка приложения: плагины, репозитории, сервисы, роуты
  config/env.ts          чтение и проверка переменных окружения
  db/
    client.ts            пул подключений PostgreSQL и экземпляр Drizzle
    migrate.ts           применение миграций (используется в Docker)
  plugins/
    error-handler.ts     единый формат ошибок
    swagger.ts           OpenAPI и Swagger UI
  shared/                общие схемы, типы, ошибки, работа с датами
  modules/
    habits/              привычки
    checkins/            отметки и статистика
    health/              проверка работы сервера
drizzle/                 SQL-миграции
```

Каждый модуль разделён на слои:

| Файл | Ответственность |
|---|---|
| `*.routes.ts` | HTTP: маршруты, схемы, статус-коды |
| `*.schemas.ts` | TypeBox-схемы — источник правды для валидации и типов |
| `*.types.ts` | Типы, выведенные из схем |
| `*.service.ts` | Бизнес-логика и правила |
| `*.repository.ts` | Интерфейс хранилища и реализация в памяти (для тестов) |
| `*.repository.pg.ts` | Реализация хранилища на PostgreSQL |
| `*.table.ts` | Описание таблиц для Drizzle |

Сервисы зависят только от интерфейсов репозиториев, поэтому хранилище можно заменить, не трогая бизнес-логику и роуты.
